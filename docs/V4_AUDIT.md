# V4.0.0 런타임·매수 경로 감사

2026-09-11. 기준 소스 V3.0.1 → V4.0.0. 이 문서는 V2/V3 인수인계 문서 중 주문 처리와 진단 관련 설명을 대체합니다.

## 결론

‘매수가 없다’는 사실만으로 엔진 고장과 전략 대기를 구분할 수 없었습니다. V3.0.1은 시장 목록 문제를 고쳤지만, 진입 거절 사유를 저장하지 않았고 재시작·네트워크·체결 처리 결함도 남아 있었습니다. V4는 원인을 관측할 수 있게 하고 확인된 결함을 수정합니다. 거래 횟수를 늘리기 위해 비용/품질 기준을 낮추는 변경은 없습니다.

## 공개 시장 관측

API 키 없이 V3.0.1 전략을 300초 실행한 진단에서 허용 KRW 250종목, 체결 메시지 3,743개, 진입 평가 665회를 관측했습니다. 473회는 예상 움직임 대비 거래비용 부족, 192회는 호가 부재/지연이었습니다. WebSocket 오류는 0건이었습니다.

이는 해당 짧은 시장 구간의 재현 결과이지 과거 실행의 정확한 원인이나 미래 거래 빈도를 입증하지 않습니다. 진단은 편도 수수료 0.05%를 가정하며 계정별 실제 수수료는 조회하지 않습니다. 공개 진단 도구는 상위 24개 후보를 직접 구독하므로 실제 엔진의 최소 체류시간 정책과는 다릅니다. 새 후보가 처음 호가를 받기 전의 평가도 ‘호가 데이터가 오래됨’에 포함됩니다.

실제 앱은 `orders/chance`로 계정 수수료를 확인합니다. `ExpectedMove`는 최근 30초 절대 변동폭 분포의 proxy이며 미래 수익 예측 모델이 아닙니다. 편도 수수료 0.05%만 가정해도 왕복 비용은 0.1%이고 기존 진입 조건은 여기에 스프레드 등을 더한 비용의 2배를 넘는 변동폭을 요구합니다. 조용한 시장에서 장시간 거래하지 않을 수 있습니다.

수정 후 별도의 300초 관측에서는 250종목, 체결 메시지 4,191개, 진입 평가 710회, WebSocket 오류 0건을 확인했습니다. 비용 부족 468회, 호가 부재/지연 201회, 모멘텀 미확인 31회, 품질 대기 9회, **BUY 신호 1회**였습니다(Q=0.837). 실제 주문은 0건입니다. 시장 구간이 다르므로 두 관측을 성능 개선률로 비교할 수 없습니다. BUY는 전략의 1차 진입판단이며 실제 계정 잔고·호가 규모·최종 비용 필터 통과나 실체결을 의미하지 않습니다.

## 주문 상태와 재시작

1. 고유 identifier와 주문 목적을 `order_intents`에 영속 저장합니다.
2. 실거래 주문은 한 번 제출합니다. POST 429는 자동 재전송하지 않습니다.
3. done/cancel과 체결 상세가 확인되면 실제 체결량을 원자적으로 반영합니다.
4. timeout/5xx/응답 유실/조회 실패는 pending으로 남겨 identifier로 조회합니다.
5. pending이 있으면 신규 매수를 차단합니다. 해당 종목의 중복 매도도 차단합니다. 다른 기존 포지션은 계속 관리합니다.
6. 재시작 후 같은 DB에서 pending을 복구합니다. 잠깐의 404로 미체결을 단정하지 않습니다.

pending이 계속 조회되지 않는 경우에는 거래소 주문 내역과 identifier를 대조해야 합니다. UI에서 임의로 지우거나 자동으로 새 주문을 내는 기능은 제공하지 않습니다. POST 직전 프로세스가 중단된 극단적인 경우 실제 미제출 의도가 pending으로 남을 수 있으며 이 경우도 사람의 확인이 필요합니다.

## 검증 범위와 남은 과제

- 실제 특징 계산을 사용하는 합성 체결/호가 → 진입판단 → 가짜 거래소 → DB 체결 기록 통합 테스트. 높은 비용에서는 같은 신호의 주문 차단도 검증.
- 재시작 구독, 일시 잔고 오류, 경보 변경, 부분 체결, 응답 유실 복구, 종료 직전 경합, 원자적 중복방지, POST 429 회귀 테스트.
- 실제 Public REST 시장 탐색과 Public WebSocket 수신 검증. 실제 자금 주문, OS 저장 키 로드, 운영 DB 수정은 수행하지 않음.
- 수익성·장기간 무중단 운전·실거래 주문 권한/IP 등록은 이번 검증으로 입증되지 않음.
- 건강도 0은 기존 실거래 손실 방어 정책을 유지하며 명시적으로 표시. 가상 성과 기반 자동 복귀는 미구현이고, 거래가 없다는 이유로 0을 강제로 해제하지 않음.
- Kelly 추정, 상관관계 제어, 장기 L2 recorder/replay, private WebSocket, pending 수동 대조 UI는 별도 개발 과제. 유효 신호의 자금배분은 기존 동적 공식을 유지하므로 한 종목 비중이 커질 수 있음.
- 최소 주문금액 미만의 미청산 관리 수량은 진단과 함께 보존될 수 있어 DRAINING이 기다릴 수 있음. 긴급 정지는 매도 없이 엔진만 중단.

## 실행 및 배포

```sh
python -m pip install -e ".[dev]"
pytest -q
python scripts/smoke_upbit_public_ws.py --timeout 20 --attempts 3
python scripts/diagnose_public.py --seconds 300 --output public-diagnosis.json
```

`main` 반영 시 Windows Release workflow가 테스트·공개 시세 검증·실행파일 빌드를 마친 후 `V4.0.0` Release를 생성합니다. 앱의 업데이트 버튼은 기존 Keyring/DB를 유지합니다. V4의 주문 기록은 이전 버전이 이해하지 못하므로 pending이나 관리 포지션이 있을 때 이전 실행파일로 되돌리지 마세요.

## 공식 API 확인

- [주문 생성](https://docs.upbit.com/kr/reference/new-order): best + IOC, 고유 identifier.
- [개별 주문 조회](https://docs.upbit.com/kr/reference/get-order): UUID 또는 identifier 조회, 주문조회 권한 필요.
- [요청 수 제한](https://docs.upbit.com/kr/reference/rate-limits): REST/WS 그룹 제한과 429/418 대응. 기존 private 요청 간격 1/11초는 현재 order 12회/초 한도 아래입니다.
